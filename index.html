Samsung R&D: what I actually did

Software Engineer, TV Product Group, Samsung R&D Institute India – Delhi (Jul 2022 – Aug 2026, after a 6-month internship). Premium Smart TVs run Tizen, an embedded Linux OS, and ship to ATSC, DVB and ISDB regions. Each year had two halves: about 4 months getting new models ready for the factory, and about 8 months improving TVs already in people's homes through over-the-network updates.

Where I worked in the firmware lifecycle

Kernel & memory debugging

  1. Flash a KASAN / AddressSanitizer image onto the TV or EVK board (it runs very slowly).
  2. Drive real actions: HDMI plug and unplug, volume, app launches like Netflix.
  3. Watch kernel logs for "tainted" and error reports, and capture logs at the moment of failure.
  4. Match each report to the physical action that caused it, then raise a defect with logs for the developer.
heap-use-after-freebuffer overflowmemory leakcore dump

I ran the sanitizer images and triaged from the logs. The developers wrote the code fixes.

Memory & performance

  • Memory profiling of every binary before a release went to market.
  • Package dependency analysis on the display Linux package to cut memory footprint on low-RAM models.
  • Worked on a daemon that watches CPU, flash and RAM use of every process and cleans up on excessive use.
  • Boot time and power trade-offs against UI lag and responsiveness, measured per process in milliseconds against spec.

Logs & new hardware

  • Read serial and UART logs from performance images to narrow problems down to OS level.
  • Validation started from scratch on buggy vendor EVK boards that crashed from day one.
  • When 16 EVK boards overheated and went black, I worked with the HQ hardware team to find the cause and get them back.
  • Planned and justified test-unit allocation across QA, product and developers.

Release & hotfix engineering

  • Built full and hotfix firmware images in Perforce and cherry-picked changelists into release images.
  • Never accepted a fix blind: built a private image, tested it on a TV, and sent it back with video and logs if it failed.
  • For risky fixes, built two images, one with the fix and one without, and shipped only once the side effect was ruled out. Example: an audio-driver fix that could make the volume UI disappear.
  • 350+ fixes across 5 chipsets, 95% within target schedule.

Test infrastructure

  • Long-run suites that simulate real use and catch CPU deadlocks on 4-core hardware.
  • Remote multi-device testbed for long-run and field tests on many TVs at once.
  • Long user paths scripted as command sequences (Netflix → YouTube → HDMI → volume → SmartThings), not pressed by hand on a remote.
  • Python tools over serial: pre-production checks, changelist checks from firmware XML, hotfix data validation.

People & coordination

  • Main link between the Delhi product team and QA, and between Delhi and Samsung HQ in Korea.
  • Negotiated test-round counts and which fixes moved to a later round.
  • Coordinated field testers in five regions, and planned test schedules around Diwali and Chuseok.
  • Mentored 4 interns on memory profiling, leak detection, sanitizer images and log analysis.
Ownership

A full TV launch, run alone

A North American model for the Black Friday sale. Product validation and release normally takes 3–4 engineers; I ran it on my own: QA meetings, sanitizer and memory passes, and holiday-risk planning.

After the October holidays, critical boot-time and UI-performance defects were still open and beyond my authority. I took them to the HQ product manager, so HQ QA could decide whether to change the spec or accept them.

Shipped on time for Black Friday.
Attention to detail

The last-day catch

On the final factory-image day, a developer's build had the right changes but used an outdated configuration data file. I spotted it from the file name as soon as the file appeared.

The fix landed in about 2 hours and I rebuilt the factory images in the next 2–3. I opened a group chat with HQ to find the root cause: one wrong file name in one section.

No bad firmware reached the factory, and the deadline held.
Judgement

A China release, solo

A 5–6 week release for an Android-on-Tizen chipset for the Chinese market. I set up the project, drove the QA meetings and decided with developers which changelists belonged in the build.

Many changes were shared across chipsets. I kept out a home-screen UI fix that was correct elsewhere but wrong for the different Chinese UI.

Hit the factory date, so mass production started on time.

SLAM lab: TortoiseBot

IIT Delhi Executive Programme in Robotics, Mar–Sep 2025. I assembled a TortoiseBot (8 GB Raspberry Pi, YDLiDAR S2, IMU, motor driver, Pi camera), brought it up over SSH, and ran teleoperation, Cartographer mapping and Nav2 navigation in ROS. Every image below is a real screenshot from my own runs.

Screen recording, 2 Aug 2025. Driving the robot from the keyboard (left) while RViz shows LiDAR points piling up in rings. Old points stayed on screen and showed up as fake obstacles along the robot's path. I tracked this defect down and fixed it.

What I did

  • Full hardware assembly and wiring of LiDAR, IMU, camera and motor driver.
  • Robot bring-up and teleoperation over SSH from the laptop.
  • Occupancy-grid mapping with Cartographer, and autonomous navigation with Nav2.
  • Fixed build conflicts between the Nav2, Cartographer and BehaviorTree packages.
  • Used rqt_graph and TF views to check that every node and frame was connected.

Samsung R&D · Python

Factory firmware registration automation

Each firmware set (12–26 GB) had to be registered by hand for the factory: about 20–25 minutes each, 6–7 per engineer, and one mistake could scrap a batch of 5,000–10,000 TVs. I built an OCR + OpenCV + PyAutoGUI uploader that runs unattended overnight, plus a separate checker that proves every image is byte-identical to the repository copy by checksum.

It was adopted across the TV Product Group and caught colleagues' errors before they reached the factory. I later led three interns who added a React front-end.

Samsung R&D · Java

Defect-tracker bulk creator

One fix often touches many files across a package, and each needed its own linked "child" record. The stock tool took about 45 seconds per record and crashed after 10–15. I built a Java client on APIs supplied by Samsung HQ that creates 40–200 linked records in seconds, with project, date and developer filled in automatically.
