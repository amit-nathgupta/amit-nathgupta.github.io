About me

Who I am

I'm an electronics engineer (BIT Mesra) turned robotics student. At Samsung I worked where software meets hardware: flashing debug images onto new boards, reading kernel and serial logs, tracing crashes back to what was physically happening on the device, and getting firmware safely to the factory.

Robots need the same skills, with more moving parts. At Manchester I'm taking that debugging discipline to mapping, perception and manipulation on real hardware.

Career goals & research interests

Goal: after my MSc, a role as a robotics software, SLAM, or test and simulation engineer, where four years of embedded debugging and release discipline are a real advantage.

MSc team project · 2026–27 In progress

Leo Rover: colour-sorting robot

Team 7 is building a rover that searches an area on its own, picks up coloured blocks with a myCobot arm and drops each one in the matching bin. My part is vision: finding the blocks with the RealSense colour camera and measuring their 3D position with its depth sensor.

First tests (Oct 2026)

  • Brought up the RPLidar and the RealSense D435 on the rover, and viewed the lidar scan live in RViz from a laptop.
  • Full-size depth video (848×480, 30 fps) reached only about 5–7 fps on the rover's Raspberry Pi, so vision processing should run on the on-board Intel NUC.
  • YOLO11n on a laptop CPU took about 95 ms per frame. The pretrained model called our red block a "hot dog", and a model I trained on a public, top-down block dataset found almost nothing from a side view. Next: training on our own low-angle images.

A year in TV firmware

Commercialisation

About 4 months · getting new models ready for the factory
  • HQ kickoff with 200–300 new features; in one kickoff 24 were assigned to me, each tested on its own private image.
  • About 1.5 months of product validation, with test and regression rounds across hardware and software.
  • Near the deadline, full builds give way to hotfixes; final images go to the factory for batches of 5,000–10,000 TVs.

Post-market updates

About 8 months · improving TVs already in people's homes
  • The factory image becomes the base; fixes and features reach TVs over the network in rounds of about 1.5 months.
  • Regression testing on every new build, plus field testing in five regions.
  • Change requests from HQ explained to QA testers, so they could write and run test cases.

What I did

Kernel & memory debugging

  1. Flash a KASAN / AddressSanitizer image onto the TV or EVK board (it runs very slowly).
  2. Drive real actions: HDMI plug and unplug, volume, app launches like Netflix.
  3. Watch kernel logs for "tainted" and error reports, and capture logs at the moment of failure.
  4. Match each report to the physical action that caused it, then raise a defect with logs for the developer.
heap-use-after-freebuffer overflowmemory leakcore dump

On TV firmware, I ran the sanitizer images and traced failures from the logs; each component's developers wrote the code fixes. The tools I wrote myself are under Tools I built.

Memory & performance

  • Memory profiling of each binary before a market release, hunting leaks, crashes and deadlocks through crash dumps and call stacks.
  • Package-dependency analysis on the display Linux package to cut memory use on low-RAM models.
  • Worked on a daemon that watches CPU, flash and RAM use of every process and cleans up on excessive use.
  • Tracked boot-time and responsiveness defects per process in milliseconds against spec, and mediated the trade-off between richer animations and boot time on a 4-core CPU.

Release & hotfix engineering

  • Built full and hotfix firmware images from Perforce Helix changelists, and cherry-picked fixes into release images.
  • Triaged defects by severity and component, and checked fixes on a private image on a real TV before accepting them.
  • For risky fixes, built two images, one with the fix and one without, and shipped only once the side effect was ruled out.

Test infrastructure

  • Long-run suites that simulate real use and catch CPU deadlocks, on a remote multi-device testbed for many TVs at once.
  • Long user paths scripted as command sequences (Netflix → YouTube → HDMI → volume → SmartThings), not pressed by hand on a remote.
  • Python tools over serial: factory-key checks before mass production, changelist tracking from firmware XML, hotfix data validation.
  • Anomaly checks comparing real user scenarios with ideal runs, to flag operating-time and user-experience regressions.

Coordination & risk

  • Main link between the Delhi product team and QA, and between Delhi and Samsung HQ in Korea.
  • Coordinated field testers in America, Poland and the rest of Europe, Korea, and Chennai in India.
  • Negotiated test-round counts and which fixes moved to a later round, and planned around Diwali and Chuseok.
  • Justified test-unit allocation, and managed schedule dependencies on third-party apps such as Netflix.

Mentoring

  • Mentored 4 interns on memory profiling, leak detection and sanitizer images.
  • Led three of them on my automation tool: work tracked on Jira, code reviewed, React front-end built on my Python code.
  • Trained one from scratch on a commercialisation project: serial logs, image types, regions, and how to raise a defect.

Tools I built

Built by me · Python

Factory firmware registration automation

Each firmware set (12–26 GB) had to be registered by hand for the factory: about 20–25 minutes each, 6–7 per engineer and 48–60 per cycle across the group, and one mistake could put a factory batch of 5,000–10,000 TVs at risk. I built an OCR + OpenCV + PyAutoGUI uploader that runs unattended overnight, plus a separate checker that compares each image with the repository copy by checksum.

The idea and the checksum check came from my director; I designed and built both tools in Python over about two months. It turned a four-person, two-hour job into a one-person job, was adopted across the TV Product Group, and caught colleagues' errors before they reached the factory. I later led three interns who added a React front-end.

Defect-tracker bulk creator

One fix often touches many files across a package, and each needed its own linked "child" record. The stock tool took about 45 seconds per record and crashed after 10–15. I built a Java client on APIs supplied by Samsung HQ that creates 40–200 linked records in seconds, with project, date and developer filled in automatically.

A Black Friday release, run solo

A premium North American model for the Black Friday sale. Product validation and release usually take 3–4 engineers; I ran both on my own: QA meetings, sanitizer and memory passes, and holiday-risk planning.

After the October holidays, critical boot-time and UI-performance defects were still open and beyond my authority. I took them to the HQ product manager, so HQ QA could decide whether to change the spec or accept them.

Shipped on time for Black Friday.
Attention to detail

The last-day catch

On the final factory-image day, a developer's build had the right changes but used an outdated configuration data file. I spotted it from the file name as soon as the file appeared.

The fix landed in about 2 hours and I rebuilt the factory images over the next 2–3 hours. I then worked with HQ to trace the root cause: the file name had been entered wrongly in one section.

The wrong file never reached the factory, and the deadline held.
Judgement

A China-market release, start to finish

A 5–6 week release for an Android-on-Tizen chipset for the Chinese market. I set up the project, drove the QA meetings and decided with developers which changelists belonged in the build.

Many changes were shared across chipsets. I kept out a home-screen UI fix that was correct elsewhere but wrong for the different Chinese UI.

Hit the factory date, so mass production started on time.

Every image below is from my own runs. TortoiseBot kit and base software by RigBetel Labs.

Screen recording, 2 Aug 2025. Driving the robot from the keyboard (left) while RViz shows LiDAR points piling up in rings. Old points stayed on screen and showed up as fake obstacles along the robot's path. I tracked down the cause and fixed it, so old points no longer stayed on screen.

  • Occupancy-grid mapping with Cartographer, and autonomous navigation.
  • Fixed build conflicts between the navigation, Cartographer and BehaviorTree packages.
